# Code Tour

用少量步骤帮助读者找到入口、理解主要流程、定位关键代码。

## 怎么做

1. **确定范围**：读取项目要求、目标 Tour 和指定入口，确认新建、修改或只检查；不明确时先问。
2. **核对源码**：从真实入口开始，包括 test 方法；确认调用、顺序、条件、数据范围和文件/网络操作。旧 Tour 仅供参考。
3. **先看主要流程**：第一站定位入口，第二站定位主要流程方法；用 `1`、`2`、`3` 标记其中的关键调用。
4. **再看子方法**：调用点后立即定位重要的被调方法，如 `1-1`，再用 `1-1-1` 表示内部步骤。简单辅助方法直接定位实现，不机械重复“调用点＋方法入口”。
5. **按深度优先顺序阅读**：看完 `1` 的内部步骤，再返回 `2`；共用步骤只说明一次，其余注明编号。独立入口分区，条件分支标明条件。
6. **删减并检查**：逐句判断是否有必要，核对源码位置、JSON、编号和顺序；展示文件并简述检查结果。

## 语言与内容

- **简单、准确、易懂**。使用计算机基础词汇和必要业务词，直接说查询、计算、筛选、导出、读取、发送、截图等动作。
- 标题说清“做什么”，如“查询商品”“导出表格”；不用“完整数据文件编排”等抽象名称，不用互联网黑话。方法名由源码定位或必要引用提供。
- 默认标题加一句必要说明；标题和源码已说清时，正文可以省略，不为每步凑句子。
- 只补关键条件、日期/统计范围、数据变化和影响结果的风险。源码自明的循环、赋值、编码、日志和 HTTP 字段留给源码。
- 同一个事实只在最合适的位置说明；父步骤讲整体，子步骤补具体条件，不逐层重复。
- 优先正面说明实际行为。删掉无用的“不是……”“不读取……”“不会……”；保留能避免误操作或误解结果的说明，如删除旧文件、缺文件终止、发送失败。
- **删掉一句不影响理解，就删。** 简短不能改变业务含义；遇到日期或功能名称易误解时，用准确名称代替长篇纠正。

## 层级示例

```text
入口：test.send()
发送流程：Service.send()
1 发送图片                  → 调用点
  1-1 分组发送图片          → 被调方法入口
    1-1-1 扫描图片
    1-1-2 发送标题
    1-1-3 发送图片
2 发送第一份表
  2-1 上传并发送文件
    2-1-1 上传文件
    2-1-2 发送消息
3 发送第二份表              → 使用 2-1
```

CodeTour 的 steps 是平面列表；标题编号表示调用归属，循环和条件由文字说明。

## 格式与检查

使用项目已有 JSON 格式，`file` 为项目相对路径，`line` 为当前 1-based 行号，`description` 为 Markdown。

```json
{
  "$schema": "https://aka.ms/codetour-schema",
  "title": "文件发送",
  "steps": [
    {"file": "src/main/java/example/SendService.java", "line": 42, "description": "# 1 发送图片"}
  ]
}
```

- 检查 JSON、字段类型、源码文件、行号附近的实现、父编号和阅读顺序。
- 核对调用、条件、日期、统计范围及文件/网络操作；不要仅查行号，也不要用正文关键词出现次数判断结构正确。
- 做一次删除检查：重复说明、无用否定和实现细节删去，必要条件和风险保留。
- `nextTour` 匹配目标 title；删除旧 Tour 时修正跳转。
- 区分 JSON 解析、Schema 校验和插件播放，只报告实际做过的检查。

## 工作边界

- 计划或只检查时不写文件；获准后才修改。保留已有有效内容，删除、重排或大改须有授权；对比版另建。
- 只读相关源码，不改业务代码、不运行 Maven/构建、应用、数据库、同步或真实请求/发送，不安装依赖，不 Git 暂存提交。
- 不复制密码、Webhook 或 Token；只描述已有能力，不猜测重试、幂等或送达保证。
